## Entry 1: November 6, 2026 - JWT Security Setup & Stateless RBAC
* **Target Category:** Authorisation & Access Control
* **What I asked for:**
  > "Write a Spring Security config with JWT authentication and role-based access control for a Spring Boot 3 app."
* **What the tool produced:**
  The AI provided a configuration class extending `WebSecurityConfigurerAdapter`, using deprecated `.antMatchers()`, enabling HTTP basic authentication, and hardcoding a static HMAC secret directly into the source file.
* **What was wrong with it:**
  `WebSecurityConfigurerAdapter` was deprecated in Spring Security 5.7 and completely removed in Spring Boot 3 / Spring Security 6, resulting in immediate compilation failure. Furthermore, hardcoding the HMAC secret key directly in Java source code exposes secrets in git history, and leaving default session creation enabled contradicts stateless REST API design.
* **What I did instead:**
  I rewrote the security architecture using modern `SecurityFilterChain` beans with `SessionCreationPolicy.STATELESS`. I moved the JWT secret into `application.properties` with environment variable interpolation (`${balancevault.jwt.secret}`). I implemented `JwtAuthenticationFilter` extending `OncePerRequestFilter`, built `JwtService` using JJWT `0.12.5`, and configured role-based access control distinguishing `ROLE_USER` from `ROLE_ADMIN`.
* **Commit Link:** [Commit b368f88](https://github.com/pallelliTulasi/LedgerLine/commit/b368f88e938b1e50d308ace7b3ec1c9bc0d1de7b)

## Entry 2: November 6, 2026 - Transaction Audit Trail & Idempotency
* **Target Category:** Audit Trail & Data Integrity
* **What I asked for:**
  > "How to transfer money between accounts and keep a history log in Spring Boot."
* **What the tool produced:**
  The AI wrote a controller method that updated account balance integers directly and logged transfer events to the terminal using `System.out.println("Transferred " + amount + " from " + from + " to " + to);`.
* **What was wrong with it:**
  Printing to stdout does not constitute an audit trail; terminal logs vanish whenever a container or process restarts. Crucially, the code lacked database atomicity—if a server failure occurred midway, funds could be deducted from the sender without crediting the recipient. It also provided no protection against duplicate transfer retries.
* **What I did instead:**
  I engineered an immutable `LedgerEntry` JPA entity with non-updatable audit fields (`transactionId`, `fromAccountNumber`, `toAccountNumber`, `amount`, `status`, `timestamp`) and a `LedgerEntryRepository`. I wrapped transfer logic in `@Transactional(isolation = Isolation.READ_COMMITTED)` and added an idempotency check (`findByTransactionId`) to ensure retransmitted requests return the previous record without deducting balances twice.
* **Commit Link:** [Commit 9b6513a](https://github.com/pallelliTulasi/LedgerLine/commit/9b6513a9047453073dbea1c590d5c0715c349041)

## Entry 3: November 6, 2026 - CORS Filter Execution Order in Spring Security
* **Target Category:** Access Control & Network Security
* **What I asked for:**
  > "React frontend on Render is getting AxiosError: Network Error when calling my Spring Boot backend. How to fix it?"
* **What the tool produced:**
  The AI suggested adding `@CrossOrigin(origins = "*")` at the top of my REST controller classes.
* **What was wrong with it:**
  Spring Security's filter chain executes before Spring MVC controllers. When the browser sends an HTTP `OPTIONS` preflight request, Spring Security rejected it as unauthenticated (401/403) before the `@CrossOrigin` annotation on the controller was ever evaluated. Additionally, using wildcard `*` with credentials violates browser security specifications and exposes APIs to cross-origin abuse.
* **What I did instead:**
  I created an explicit `CorsConfigurationSource` bean integrated directly into the `SecurityFilterChain`. I configured explicit permission for preflight requests (`requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()`) and whitelisted only authorized origins (`localhost:5173`, `*.onrender.com`, `*.vercel.app`) with allowed methods and exposed rate-limit headers.
* **Commit Link:** [Commit 7e92b8f](https://github.com/pallelliTulasi/LedgerLine/commit/7e92b8fc57ec718e2fe13b19280dff863b12368d)

## Entry 4: November 6, 2026 - Cloud Database Secrets & Dynamic URI Parsing
* **Target Category:** Secrets Management & Production Resilience
* **What I asked for:**
  > "Give me the application.properties configuration to connect my Spring Boot app to Render PostgreSQL."
* **What the tool produced:**
  The AI produced a static `application.properties` snippet with hardcoded plaintext database credentials: `spring.datasource.url=jdbc:postgresql://ep-xyz.render.com:5432/ledgerline_db`, `spring.datasource.username=user`, `spring.datasource.password=secret123`.
* **What was wrong with it:**
  Committing plaintext database credentials to a public GitHub repository violates core security practices. Furthermore, cloud platforms like Render provide database URLs in the format `DATABASE_URL=postgres://user:password@host:port/database`, which standard Spring Boot JDBC fails to parse because it requires the `jdbc:postgresql://` schema prefix.
* **What I did instead:**
  I removed all hardcoded credentials and wrote a custom `DataSourceConfig` configuration class. It dynamically inspects environment variables, seamlessly defaults to embedded H2 for zero-configuration local execution, and parses cloud `postgres://` URLs into normalized `jdbc:postgresql://` strings with credentials extracted from environment variables.
* **Commit Link:** [Commit ad1aa2b](https://github.com/pallelliTulasi/LedgerLine/commit/ad1aa2b0ef4c9fbafbb86e58f0004ff04f46ab21)

## Entry 5: November 10, 2026 - Concurrency Control & Double-Spending Race Conditions
* **Target Category:** Authorisation, Audit Trail & Financial Integrity
* **What I asked for:**
  > "How to handle multiple users transferring money at the exact same time without errors."
* **What the tool produced:**
  The AI suggested applying the Java `synchronized` keyword to the service method: `public synchronized void transfer(...)`.
* **What was wrong with it:**
  A JVM-level `synchronized` keyword only works within a single JVM process and fails completely in distributed or multi-instance cloud deployments (e.g. horizontal scaling). Furthermore, synchronizing the entire method creates an extreme throughput bottleneck by serializing all transfers globally across all accounts, instead of isolating locks to the two accounts involved.
* **What I did instead:**
  I implemented database-level row pessimistic locking using `@Lock(LockModeType.PESSIMISTIC_WRITE)` in `AccountRepository`. To eliminate deadlocks when two accounts transfer to each other simultaneously, I enforced deterministic locking order based on account numbers (`fromAcc.compareTo(toAcc)`). I wrote an automated 50-thread concurrency test (`TransactionServiceTest`) proving zero overdraft and strict conservation of total balance.
* **Commit Link:** [Commit b368f88](https://github.com/pallelliTulasi/LedgerLine/commit/b368f88e938b1e50d308ace7b3ec1c9bc0d1de7b)

## Entry 6: November 10, 2026 - Production Container Build & Memory Optimization
* **Target Category:** Infrastructure, Reliability & Cloud Deployment
* **What I asked for:**
  > "Create a Dockerfile and render.yaml blueprint to deploy the Spring Boot backend on Render free tier."
* **What the tool produced:**
  A single-stage Dockerfile that copied the entire source repository and ran `mvn spring-boot:run` directly inside the container without JVM memory flags or health check endpoints.
* **What was wrong with it:**
  Running `mvn spring-boot:run` in production consumed over 800MB of RAM, instantly exceeding Render's 512MB free container memory limit and causing Out-Of-Memory (OOMKilled) crashes on boot. Furthermore, Render requires a lightweight, unauthenticated health endpoint to determine if a web service is healthy; without it, Render marked the deployment failed after 5 minutes.
* **What I did instead:**
  I created a multi-stage `Dockerfile` (Eclipse Temurin 17 JDK builder stage -> JRE slim runtime stage) producing an optimized runnable JAR under 150MB. I added JVM container flags (`-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError`) in `render.yaml` and exposed a dedicated `/health` endpoint in `RootController` to satisfy cloud health checks.
* **Commit Link:** [Commit 1b0786a](https://github.com/pallelliTulasi/LedgerLine/commit/1b0786a60db882a17f6443c68eafe01947e4526d)
